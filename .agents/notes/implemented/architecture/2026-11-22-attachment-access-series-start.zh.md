# Agent Note: 附件路径变化会开启请求序列

Status: implemented

[English](2026-11-22-attachment-access-series-start.md) | 中文

## Problem

文件与图片句柄文本给出的是持久附件的执行世界读取路径：附件提供方的宿主对象位置经 `ctx.fs.processPathFromHostPath()` 映射后的结果。该路径有意不进入会话日志，因此每个请求都会按当时挂载的提供方重新推导一次。

这两点合在一起，使同一条已记录的消息在两个请求中以不同字节到达。会话运行期间重新挂载附件或文件系统提供方，或在另一个执行世界中恢复会话（另一个 `DSH_HOME`、被移动过的共享挂载），都会重新渲染历史上该附件在日志中已经发送过的每一处出现。提供方前缀缓存于是从首个受影响消息开始未命中，而日志中没有任何记录说明原因：`headerEquals()` 看到相同的配置与工具，因此根本没有写入 `request/header`；`session.surface.contentGeneration` 也没有变化。这次未命中真实存在，却没有归属，对任何日志消费方都不可见。

## Decision

循环在即将发送的请求上调用 `ctx.llm.attachmentAccessPaths(messages)`，取得该请求中每个持久附件出现位置的执行世界读取路径；当某个路径与该循环实例上一次请求为同一附件解析出的路径不同时，就开启一个新的请求序列。日志尚未发送过的附件只会贡献新的尾部文本，绝不开启序列；路径消失的附件（压缩移除了它的消息，或执行世界已无法读取它）不会改变任何已发送内容。

当某个循环实例在已有请求头的日志上的第一次请求中，只要有附件解析出路径，就开启序列。渲染该日志的进程可能运行在另一个执行世界中，而日志中没有任何内容能证明它没有。

标记沿用既有的、只写日志的序列信号：请求头其余部分未变时记 `reason: 'series'`；因其他原因需要写入请求头时，在 `initial`、`resume` 或 `change` 事件上带 `startsSeries: true`。不新增任何持久字段、摘要或逐请求记录；路径依然不进入日志。

因该原因开启的序列绝不归并系统提示词。归并会重新把 surface 第 0 号节点作为基线，只有在整个前缀都已丢失时才是零成本；而这次失效从首个受影响的附件消息开始，它可能位于已追加的 in-history 提示词节点之后。因此 `SystemPromptProjection` 仍然只接收 pre-step、surface 代次以及不具备能力路由的工具这几类序列事实。请求照旧携带该路由原有的提示词。

`attachmentAccessPaths()` 归属 `LlmRuntime`，因为该服务已经为 `fileRequestText()` 拥有同一套解析，并且已经同时读取附件与文件系统服务；`dsh-llm` 中的 `visitRequestAttachments()` 是遍历图片与文件出现位置的唯一遍历，因此循环无法与渲染文本的适配器产生分歧。

## Alternatives considered

**让执行世界路径不进入模型可见的句柄文本。** 这是缓存一致性审计建议的另一半，也是唯一能消除（而不是归属）这种失效的变体。予以否决，因为该路径是模型访问已上传文件的唯一途径，也是被请求上限省略的图片的唯一恢复途径：去掉它会让 `FileBlock` 内容不可读、被省略的图片无法恢复。而世界无关的引用（由文件工具在调用时解析的附件 id 或 URI）需要在文件系统接缝和每个文件工具中新增解析面，且远端执行世界并不持有附件对象的副本，因此它还会改变这些工具在读取与编辑上所能承诺的东西。

**把路径移到 runtime-context 尾部。** 路径会离开已缓存历史，重新映射时只需在其后追加一条小条目，这也是 plan 与 Team 模式状态如今到达模型的方式。暂时否决：runtime-context 贡献由提示词与工具状态装配而来，拿不到请求消息，循环必须先在准入之前派生消息，再交给插件拥有的条目；而且该条目的访问映射会随会话中每个附件增长，模型还要跨两条消息关联 id。

**在日志中保存逐附件的路径摘要。** 这样无需重新推导即可跨进程发现重新映射。予以否决：它按附件增加持久记录，并把一个派生事实变成会话状态；序列标记已经承载了可观察的后果，缓存诊断消费方可以自行重新推导路径。

**在渲染文本处发现重新映射。** 适配器知道精确字节，但它在请求头写入之后才运行，无法写入请求头；把决策放在那里会让每个提供方插件各自维护请求序列状态。

## Consequences

历史中带有可映射附件的会话在恢复时，现在会于 `resume` 请求头上记录 `startsSeries: true`，即使执行世界并未改变。就缓存归属而言这是误报，之所以接受，是因为 harness 无法证明先前的进程解析出了相同路径；该标记不改变任何模型可见字节，也不影响提示词归并。

序列开始会重置工具声明序列的基线，因此 addition-only 路由会按当前工具列表重建声明，此前由某条添加记录激活的工具会重新显示为延迟加载，直到再次被添加。这一重置是如今每次序列开始都会做的事，包括 pre-step 监听器在没有 surface 变更时声明的序列开始；而提供方反正已经丢失了该前缀。若要把附件这一情形排除在外，就需要一个独立的持久标记。

`attachmentAccessPaths()` 在每个请求上遍历请求内容。该遍历对已派生的消息只做单次扫描，不按消息分配，也不替换任何既有工作：同一请求组装随后会为适配器投影同样的出现位置。

单元测试固定图片与文件出现位置的映射，固定无提供方、无映射、畸形引用的降级结果，固定路径重新映射时写入的序列标记、新上传附件时不写入该标记，以及有可解析路径与没有可解析路径两种恢复情形。agent-loop 测试还断言该已记录消息确实以新世界的路径到达提供方，因此该标记归属的是真实存在的失效，而不是假设的失效。
